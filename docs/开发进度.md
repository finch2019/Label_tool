## 一、项目定位

通用型数据解析标注平台：数据以**文件夹**形式上传，自动解析目录结构生成分类树；检测文件夹内的 json / txt 标注文件；支持**图片**与**文本**两类数据的 AI 预标注、人工标注、复核确认与结果导出。

核心交互流程：

```
上传数据文件夹 → 自动解析（目录树 / 标注文件探测）
    → 图片页（预览模式 → 标注配置 → 独立标注页 / 批量预标注 → 复核 → 导出）
    → 文本页（数据目录 → 导入标注池 → LLM 预标注 → 独立标注页 → 导出）
    → AI 助手（对话式引导，可直达各功能）
```

## 三、关键设计说明

### 3.1 标注数据模型（annotations.json，内存加载）

```json
{
  "items": {
    "1.6万张/广告/xx.jpg": {
      "classify": {
        "label_path": "1.6万张/广告/欺诈及营销广告",
        "vlm_suggest": "…",          // VLM 建议路径
        "vlm_confidence": 0.92,
        "vlm_reason": "…",
        "status": "pending",          // pending=AI预标注待确认 / confirmed=已确认
        "ts": 1756867200
      },
      "review": { "decision": "confirm" },
      "boxes": [ ... ]                // 检测框
    }
  }
}
```

- **批量预标注结果** = `classify.status == "pending"` 且有 `vlm_suggest`（批量删除只清这类，不碰手工/复核数据）
- 无 json 镜像的数据集，框标注自动落到工具目录 `box_annotations/`
- **标注数据持久化**：`annotations.json` 落盘存储（每次读写均走磁盘），服务重启不丢；重启后总览页仍显示「读取上次记录」，点击后按持久化路径自动重新解析并恢复标注

### 3.2 批量预标注可控性（本轮重点）

- 启动：确认弹窗显示目标目录 + 实时统计未标注数 + 数量选择（20/50/100/200/全部）
- 运行：工具栏显示 ⏹停止 / 🗑删除预标注（仅启动后出现）；后端 `BATCH_VLM_STATE.stop` 标志位 + 线程池 `cancel_futures` 取消未开始任务
- 停止后已完成结果保留；状态条区分「完成 / 已停止」
- 相关接口：`POST /api/label/batch_vlm`、`GET …/status`、`POST …/stop`、`GET …/pending`、`GET …/clear_count`、`POST …/clear`

### 3.6 昵称身份与标注归属（协作 P2，2026-09-07）

**身份规则（免登录轻量方案）**
- 前端 `api()` 封装统一注入 `X-User` 请求头；HTTP 头仅允许 ASCII，昵称经 `encodeURIComponent` 编码，后端 `user_of()` 解码还原
- 昵称存 `localStorage("label_user")`；启动时若无昵称弹一次引导框（可「暂不设置」），顶栏用户徽章点击可随时设置 / 改昵称
- **未设置昵称 = 只读浏览模式**：`api()` 对所有 POST 写请求拦截，先弹窗引导设置昵称，取消则中止请求并提示；GET（图片预览 / 列表加载）不受影响
- 未携带 X-User 的请求（旧脚本 / curl）按「本地用户」处理，零感知
- 同一昵称 = 同一身份（多设备可共用），不做唯一性拒绝（显式成员管理属 P4）

**成员注册与活跃（project.json）**
- `/api/session` 及所有写操作触发 `touch_member()`：首次出现自动以 `role=annotator` 加入 `members`；`last_active` 超过 60 秒才落盘，避免高频写
- `_project_lock`（RLock）保护 project.json 读改写

**归属字段（annotations.json / 框标注镜像，向后兼容、无需迁移）**
- `items[].classify.by`（分类标注人）、`items[].review.by`（复核人）、`items[].boxes_by`（框标注归属人）
- 框标注镜像 json 顶层新增 `updated_by` / `updated_at`
- 文本标注池条目 `by`（确认人）
- 读接口同步扩展：`/api/session` 返回 `user`；复核队列项加 `label_by` / `my_by`；`/api/label/images` 加 `classify_by` / `boxes_by`；`GET /api/boxes` 加 `updated_by`

**读-改-写全量加锁（并发安全）**
- `_annotation_lock` 由 `Lock` 改 `RLock`（外层持锁后 `save_annotations` 内层可重入，避免死锁）
- 写端点全部持锁包裹读改写：classify / boxes / review decide-reset / annotate config / text import / text_pool add-decide-delete / batch_vlm clear
- `run_batch_vlm`、`run_pool_vlm` 线程池落盘的局部锁统一替换为全局 `_annotation_lock`，与前端写端点互斥；纯读端点不加锁

### 3.10 本地数据上传（浏览器直传，2026-09-10）

服务部署到服务器后，用户浏览器无法再填服务器本地路径，新增**本机数据直传**链路（导入弹窗双 tab：本地上传 / 服务器路径，后者保留兼容本机部署）：

- **两种上传方式**
  - 文件夹直传：`<input webkitdirectory>` 整文件夹选择，按 `webkitRelativePath` 还原目录结构，前端并发 4 分文件上传（单文件重试 1 次），自动过滤 `.DS_Store` / `Thumbs.db` / `__MACOSX` 等杂项
  - zip 压缩包：单请求流式上传（XHR `upload.onprogress` 显示字节级进度），服务端安全解压；压缩包内若只有单一顶层目录会自动解包（`data.zip/data/...` → 直接以 `data` 为数据源）
- **后端会话协议**：`POST /api/upload/begin`（建会话，返回 sid；无激活项目自动建「默认项目」，**不动旧数据**，顺带清扫 >24h 的孤儿 `.staging_*` / `.old_*` 目录）→ `POST /api/upload/file?sid=&relpath=`（请求体即原始文件流，攒批 4MB 经 `run_in_threadpool` 落盘避免阻塞事件循环，**无需 python-multipart 依赖**）→ `POST /api/upload/finish?sid=`（文件夹改名 / zip 解压 → 复用 `_apply_load` 解析挂载并返回探测报告）；`POST /api/upload/cancel` 丢弃暂存
- **替换语义（安全时序）**：旧数据在 `finish` 探测成功后才删除——同名旧集先改名 `.old_*` 保全，解析失败自动回滚；成功后清掉 `data/` 下其它历史数据集（单数据源语义，进行中会话的点前缀目录豁免）。对照 `/api/load`「探测成功才替换」的一致安全语义
- **存储位置**：`projects/<id>/data/<数据集名>/`（暂存 `.staging_<sid>/` 完成后原地改名），Docker 挂载卷内天然持久化；服务重启后「读取上次记录」按持久化路径恢复，与路径导入行为一致
- **安全**：`relpath` 显式拒绝 `..` / 盘符 / 绝对路径（400），zip 解压跳过路径穿越条目；`finish` 校验 zip 后缀，坏包返回 400 而非 500；数据集名消毒文件系统非法字符
- **前端**：导入弹窗改造为双 tab（本地上传 / 服务器路径），上传三态 UI（选择 → 确认(名称+摘要) → 进度条/取消），完成后复用解析报告 → 进入平台流程；上传走独立 XHR（带 X-User 头 + 进度事件），未设昵称同样先引导；上传引入 `phase` 状态机（idle/uploading/done）——**上传中关闭弹窗任务后台继续，重开弹窗按阶段恢复视图**（绝不重置进行中状态）；上传失败自动释放服务端会话并提示重新上传（无断点续传）
- **验证**：zip 嵌套解压 + 顶层解包 / begin 不提前删旧数据 / finish 后替换（同名+异名旧集均清理）/ 取消不破坏现有数据 / 非 zip 与穿越路径返回 400 / 空文件落盘 / 暂存清理，14 项 API 级测试全部通过（测试用独立 `CONFIG_FILE`，未污染真实项目）

### 3.30 翻页/关闭自动保存：修复"只保存了第一张"（2026-10-14，app.js?v=45）

**用户反馈**：连续标注多张后点保存，只有一张落盘（"点击保存不是应该保存当前及之前所有涉及的标注吗？怎么只保存了第一张"）。

**根因**：保存是**逐张即时**语义（每次只保存当前图），但存在多条"未保存就离开当前图"的路径，切图瞬间内存 shapes 被服务器数据覆盖、改动直接丢失：
- 编辑器弹层：`‹ ›` 翻图（stepEditor）与 ✕ 关闭直接切图/关层，不保存
- 独立标注页：「上一张」按钮、键盘 `←`、`→`（直接调 annoNext 未保存）、上一组/下一组、退出标注页——均不保存

**修复（改动检测 + 离开前自动保存）**：
- **改动基准**：加载标注时快照 `_original`（弹层 showEditor / 标注页 annoShow 检测分支），保存成功后刷新基准
- **editorDirty / saveAnnoIfDirty**：shapes 与基准不一致（增/删/改）才发保存请求；保存失败返回 false，调用方**阻止翻页/关闭**（防真丢）
- 覆盖入口：弹层 `‹ ›` 翻图与 ✕ 关闭；标注页「上一张」「下一张」「保存并下一张」、键盘 `← →`、上一组/下一组（annoLoadGroup 入口统一）、退出标注页
- 语义统一：「保存并下一张」无改动时直接翻页（无东西可保存）；网络失败不离开当前图，重试即可

### 3.31 弹层切图时序漏洞：修复"切了图后保存，前面的又没有了"（2026-10-14，app.js?v=46）

**用户反馈**：v45 修复后问题依旧——弹层连翻多张、每张画框，回看时前面的框丢失。

**根因（showEditor 的 rel 时序漏洞）**：弹层 `showEditor` 在函数开头就 `S.editor.rel = rel`（指向新图），随后才 `await` 图片加载 + `await` GET boxes。这个**加载窗口期内 rel=新图、shapes=旧图内容**：
- 窗口期点「保存标注」/ 连点 `‹ ›` 触发自动保存 → **旧图的框 POST 到新图**（串图污染，新图 json 被旧图内容覆盖）
- 连点翻页时，前一张的 showEditor 慢响应返回，会把**旧图 shapes 设到已切换的新图上**（竞态覆盖）

对比：独立标注页 annoShow 一直是正确写法（`rel=""` 守卫 + qi token 双保险），弹层漏了对齐。

**修复（对齐 annoShow 守卫模式）**：
- **rel 加载守卫**：showEditor 开头 `rel=""` + 清空 shapes/列表（窗口期任何保存请求被 editorDirty/显式守卫拒绝）；图片 + 标注**数据就绪后才认领新图**（`rel = rel`）
- **竞态 token**：`S._edSeq` 序号，showEditor 每次 await 后核对，连点翻页时旧请求结果直接作废
- **保存按钮守卫**：`#ed-save-boxes` 加载窗口期点击提示"图片加载中，请稍候再保存"；POST 前快照 relAt，响应回来核对——期间已切图则不更新基准/角标（服务器已落盘，切回时重载）
- **saveEditorSilent 同样加 relAt 快照核对**
- **stepEditor 防重入**：`S._edStepping` 标志，自动保存/加载未完成时忽略连点（try/finally 复位）

**数据恢复**：排查时后端实测的 testA/testB 框曾覆盖 `val/slider/1.json、2.json`，已从服务端自动备份（api_boxes_save 首次编辑前生成的 `.json.bak`）恢复为用户原始标注。
