# 共同标注功能设计（以项目为基础的多用户协作标注）

> 日期：2026-09-04
> 状态：设计稿（待评审，未实施）
> 关联文档：[开发进度.md](开发进度.md)
> 已确认的决策：轻量昵称身份（免登录）/ 混合任务分配（指派 + 抢占）/ 轮询同步（不引入 WebSocket）

---

## 一、背景与目标

当前平台是**单机单用户**工具：

- 后端全局单会话（`server.py` L55-56 `STATE`），一次只能挂载一个数据源；
- `annotations.json` 全局一份，无归属人概念；
- 无任何用户/身份机制（无 cookie、header、登录）；
- 服务绑定 `127.0.0.1:8300`。

本设计在**不推翻现有架构**的前提下，引入两个能力：

1. **项目化**：数据源、标注数据、配置以「项目」为单元隔离，可创建/切换多个项目；
2. **共同标注**：多个标注员（内网多设备访问同一服务）在同一项目内协作，支持管理员指派任务 + 成员自行抢占，标注记录归属到人，互不冲突。

非目标（本期不做）：

- 账号密码、真实权限安全（X-User 为身份标识而非安全认证，内网信任环境）；
- 实时协同编辑（两人同屏看同一张图的实时笔迹）；
- 文本线的协作改造（列入后续阶段，机制可复用）。

## 二、总体方案

```
                        ┌──────────────────────────────────────┐
                        │            projects/<id>/             │
                        │  project.json      项目元信息+成员     │
                        │  annotations.json  标注(扩展归属/认领) │
                        │  box_annotations/  框标注             │
                        │  export/           导出               │
                        └──────────────────────────────────────┘
                                     ▲
   浏览器A(张三) ── X-User: 张三 ──┐  │
   浏览器B(李四) ── X-User: 李四 ──┼── FastAPI（单进程，_annotation_lock 串行化写入）
   浏览器C(王五) ── X-User: 王五 ──┘  │
                                     │
        任务来源两条线：              │
        A. 管理员指派（assignments，指派时快照图片清单，round-robin 均分）
        B. 任务池抢占（claim 锁 + TTL 心跳，先到先得）
                                     │
        同步方式：现有轮询模式（标注页 5s 状态轮询 / 心跳 3min / 看板 30s 缓存）
```

核心原则：

1. **沿用现有存储**：仍是 `annotations.json` 单文件 + `_annotation_lock`，不引入数据库；标注条目只**扩展字段**（`by`、`claim`），不改已有字段语义，旧数据完全兼容。
2. **认领锁是唯一并发控制点**：图片级 `claim`（谁在标这张 + 过期时间），保存时校验，冲突返回 409。
3. **前端只加不改**：新增「协作」视图与昵称弹窗，标注/复核页叠加认领状态，既有流程不动。

## 三、概念模型

| 概念 | 说明 |
|------|------|
| 项目 Project | 一份数据源 + 一套标注数据的隔离单元。有唯一 `id`、名称、成员表 |
| 成员 Member | 项目内已注册的昵称 + 角色。首次以某昵称访问项目时自动加入 |
| 角色 Role | `admin`（创建者，可管理成员/指派/复核）/ `reviewer`（复核）/ `annotator`（标注）。admin 兼具全部能力 |
| 任务池 Pool | 项目数据源中「未指派且未标注」的图片集合，任何成员可抢占 |
| 指派 Assignment | 管理员创建，把一批图片（快照清单）分给一名成员，成员在「我的任务」中处理 |
| 认领 Claim | 成员对某张图片的临时工作锁，TTL 默认 10 分钟，心跳续期，保存后自动释放 |

身份规则：

- 首次访问弹出昵称输入框，昵称存 `localStorage("label_user")`；
- 前端所有请求经统一的 fetch 封装自动附带 `X-User: <昵称>` 头；
- 昵称在**项目内唯一**（重名时后端拒绝加入，提示换名）——同一人在多设备用同一昵称即视为同一身份；
- 未带 `X-User` 的请求（旧入口/脚本）按 `本地用户` 处理，单机模式不受影响。

### 4.3 annotations.json 扩展（向后兼容）

```json
{
  "version": 2,
  "items": {
    "1.6万张/广告/xx.jpg": {
      "claim": {"user": "张三", "scope": "annotate", "expires": 1756965600},
      "classify": {
        "label_path": "1.6万张/广告/欺诈及营销广告",
        "status": "confirmed",
        "by": "张三",                // 新增：标注人（手工/复核确认时写入）
        "ts": 1756867200
      },
      "review": {"decision": "confirm", "by": "李四", "ts": 1756867300},   // 新增 by
      "boxes_by": "张三"              // 新增：框标注归属（镜像 json 内同记 updated_by）
    }
  },
  "assignments": [                    // 新增顶层：指派记录
    {
      "id": "asg_01",
      "assignee": "李四",
      "dir": "1.6万张/广告",
      "images": ["1.6万张/广告/a.jpg", "1.6万张/广告/b.jpg"],
      "created_by": "张三",
      "created_at": 1756964500,
      "note": ""
    }
  ],
  "text_items": {}, "text_pool": {}, "annotate_cfg": {}
}
```

要点：

- `claim` 独立于 `classify`，可为无标注记录的图片创建条目（`setdefault` 模式，已有代码同款）；释放/保存时删除 `claim` 键，避免残留；
- `claim.scope` 取 `annotate` / `review`；同一图片同时只允许存在**一个**有效 claim（标注与复核互斥，避免边标边审）；
- 旧数据无 `by`/`claim`/`assignments` 字段 → 读取时按缺省处理，无需迁移脚本（默认项目创建时把 `version` 升到 2 即可）。

## 五、并发控制设计（认领 / 心跳 / 冲突）

### 5.1 认领流程（独立标注页）

```
标注员打开一组图片（组大小 N，沿用现有分组配置）
  │
  ├─ ① POST /api/project/claim {images: [N张]}     ← 批量认领，一次往返
  │     服务端在 _annotation_lock 内逐张判定：
  │       无 claim / 已过期 / 本人持有 → 认领成功（写 claim，expires=now+ttl）
  │       他人在持 → 失败
  │     返回 {results: [{image, ok, holder}]}
  │
  ├─ ② 前端渲染：失败的图片标记「🔒 张三标注中」，标注时自动跳过
  │
  ├─ ③ 每 3 分钟 POST /api/project/heartbeat {images: [本人仍持有的]}   ← 续期
  │
  ├─ ④ 保存 POST /api/classify 或 /api/boxes：
  │     服务端校验：若存在未过期且非本人的 claim → 409 {holder: "张三"}
  │     校验通过 → 写入标注（记 by=X-User）→ 删除 claim
  │
  └─ ⑤ 离开页面/切组：POST /api/project/release {images: [...]}
        （beforeunload 尽力而为；遗漏靠 TTL 兜底自动过期）
```

### 5.2 规则明细

| 场景 | 行为 |
|------|------|
| 两人同时抢同一张 | 两个请求都在 `_annotation_lock` 内串行判定，先到先得，后者收到 `ok:false` |
| 标注员中途关闭浏览器 | claim 存活至 TTL（默认 600s）过期，其后任何人可抢；看板上显示「超时释放」 |
| 指派图片被他人抢占 | 指派是**归属权**（advantage），不是硬锁：被指派人认领时无视他人**过期**的 claim；但活跃 claim 期间照样不可抢（先抢先标，完成后计入被指派人名下？否——计入实际标注人 `by`） |
| 保存时 claim 已被抢走（TTL 过期被人抢注） | 返回 409，前端 toast「该图已由 张三 接手」，自动跳下一张 |
| 复核认领 | `POST /api/review/queue` 取到当前复核项后调 `claim(scope=review)`；复核队列本身按人过滤「已被他人 review 锁定」的项 |
| 未标注直接跳过 | 调 release，不产生任何标注记录 |

### 5.3 写入原子性

现状读操作不加锁，多用户下必须收紧为：**所有「读 annotations → 修改 → 写盘」的代码段统一持 `_annotation_lock`**（涉及 `/api/classify`、`/api/boxes`、`/api/review/decide`、`claim/heartbeat/release`、批量 VLM 的单条落盘已自带局部锁，可合并为全局锁）。单文件 + 全局锁在 ≤10 人内网并发下没有性能问题（写入频率为「人次级」，非毫秒级高频）。

## 六、任务分配设计（混合模式）

### 6.1 指派（管理员）

- 入口：协作页「任务分配」面板。参数：目标目录（目录树选择）+ 每人数量 + 勾选成员；
- 服务端 walk 目标目录取**未标注**图片（复用 `collect_pending_images`，内部已有过滤），按勾选顺序 round-robin 均分，生成 N 条 assignment（图片清单**指派时快照**，避免每次请求重复 walk，也保证任务不因目录变动漂移）；
- 指派后：
  - 被指派人「我的任务」队列前置；
  - 这些图片在任务池中对**其他人**仍可见（不隐藏），但标注时归属 `by` 记实际操作人——管理上由 admin 看板发现越界标注；
- 回收：admin 可撤销未开工（无人认领/未标注）的 assignment；已部分完成的可只撤销剩余图片。

### 6.2 抢占（任务池）

- 现有独立标注页的取图逻辑保持「目录 + 分组」，仅在前端加一层：**组内图片先批量 claim，抢不到的标记跳过**；
- 「只看未标注」筛选项语义扩展为「未标注且未被他人活跃认领」。

### 6.3 标注页取图优先级

```
我的任务（assignments.assignee == 我，按创建时间）
  ↓ 取完
任务池（当前配置目录内未标注图片）
```

配置弹窗新增「任务来源」胶囊选项：`自动（推荐）/ 仅我的任务 / 仅任务池`。

## 七、API 设计

> 除注明外均需 `X-User` 头。角色校验失败返回 403，认领冲突 409。

### 7.1 新增端点

| 方法 | 路径 | 角色 | 说明 |
|------|------|------|------|
| GET | /api/projects | 任意 | 项目列表 `[{id, name, source, member_count, my_role}]` |
| POST | /api/projects | 任意 | 创建项目 `{name, source}` → 创建者为 admin 并自动激活 |
| POST | /api/projects/{id}/activate | 成员 | 切换激活项目（内部执行现 /api/load 流程） |
| GET | /api/project/info | 成员 | 当前项目元信息（含成员表；非成员自动注册为 annotator） |
| POST | /api/project/member/role | admin | `{name, role}` 调整角色 |
| DELETE | /api/project/member/{name} | admin | 移除成员（其历史标注保留，`by` 不变） |
| POST | /api/project/assign | admin | `{dir, per_count, assignees: [], note}` → 均分生成 assignments |
| GET | /api/project/assignments | 成员 | admin 返回全部；成员返回自己的（含各条完成数） |
| POST | /api/project/assignments/{id}/revoke | admin | `{only_remaining: true}` 撤销（可只撤剩余） |
| POST | /api/project/claim | 成员 | `{images: [], scope}` → 批量认领 `[{image, ok, holder}]` |
| POST | /api/project/heartbeat | 成员 | `{images: []}` → 续期，返回仍持有的清单 |
| POST | /api/project/release | 成员 | `{images: []}` → 释放本人认领 |
| GET | /api/project/progress | 成员 | 看板数据（30s 缓存），见 7.3 |

### 7.2 改造端点

| 端点 | 改动 |
|------|------|
| POST /api/classify | ① claim 校验（他人活跃持有 → 409）② 写入 `classify.by` ③ 成功后释放该图 claim |
| POST /api/boxes | 同上；镜像 json 顶层写 `updated_by` |
| POST /api/review/decide | ① 角色 ≥ reviewer ② 写 `review.by` ③ 复核 claim 释放 |
| GET /api/label/images | 响应项增加 `claimed_by`（活跃 claim 持有者，非本人前端显示锁标）、`assignee`（被指派人） |
| GET /api/review/queue | 过滤被他人 `scope=review` 活跃锁定的项；响应增加 `claimed_by` |
| GET /api/session | 增加 `project_id/project_name/user`（从 X-User 解析） |
| POST /api/assistant | 新增 action：`open_collab`（打开协作页） |

### 7.3 GET /api/project/progress 响应示例

```json
{
  "total": 21000, "annotated": 3520, "reviewed": 812,
  "members": [
    {"name": "李四", "role": "annotator", "annotated": 1200, "reviewed": 0,
     "active_claims": 15, "assigned_done": 300, "assigned_total": 500,
     "last_active": 1756965100}
  ],
  "assignments": [{"id": "asg_01", "assignee": "李四", "total": 500, "done": 300}]
}
```

统计口径：`annotated` 按 `items[*].classify.by` 聚合；`reviewed` 按 `review.by` 聚合；`last_active` 由带 X-User 的写操作刷新到 project.json。

## 九、兼容与迁移

1. **自动迁移**：启动时若 `projects/` 不存在（或为空）且 `config.json` 存在有效 `source` → 创建「默认项目」：搬移现有 `annotations.json` → `projects/<id>/annotations.json`（`version: 2`），`box_annotations` 沿用旧路径（写入 project.json），并设为 `active_project`。旧全局 `annotations.json` 保留只读备份，不再写。
2. **旧客户端/脚本**：无 `X-User` 的写操作按 `本地用户` 记 `by`，不拒绝——单机工作流零感知。
3. **导出格式不变**：txt/csv/YOLO/COCO 内容与现在一致（不含归属字段）；可选在 xlsx 类导出中追加「标注人」列（文本线后续阶段处理）。
4. **数据隔离**：所有既有端点行为仅作用于激活项目；`/api/tree`、`/api/image`、越界校验（`source_abs()`）逻辑不变。

## 十、性能与风险

| 风险 | 评估 | 对策 |
|------|------|------|
| annotations.json 全量重写放大 | 2.1 万 item 约几 MB，写频率为人次级 | 可接受；若未来 >10 人或文件 >20MB，再评估迁移 SQLite（存储层单点替换，API 不变） |

## 十二、验收要点（双浏览器并开模拟）

1. 甲创建项目 → 乙以新昵称访问自动加入为 annotator；
2. 甲乙同时打开同目录同组 → 各自抢到的图片不重叠，重叠部分一方显示🔒；
3. 甲标注保存后，乙的网格刷新可见已标注状态与归属人；
4. 甲认领后直接关闭浏览器 → 10 分钟后乙可抢；
5. 管理员指派 100 张给乙 → 乙「我的任务」出现且优先出队，进度看板任务完成数递增；
6. 乙尝试复核（无角色）→ 403 提示；提升为 reviewer 后可复核；
7. 服务重启 → 「读取上次记录」恢复激活项目，claim 全部过期失效，标注与归属完整；
8. 旧请求（无 X-User）标注 → 归属「本地用户」，无报错。
